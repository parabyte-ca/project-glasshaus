# Security baseline (OWASP ASVS 4.0 Level 2)

How Project Glasshaus meets the ASVS L2 areas that apply to it, and what operators must do.

| Area | Implementation |
| --- | --- |
| V1 Architecture | One service layer behind REST, MCP and the worker; Postgres row-level security isolates organizations even if a filter is missed; the app connects as a role without `SUPERUSER`/`BYPASSRLS` and refuses to start otherwise in production. |
| V2 Authentication | Argon2id password hashes; 12–1024 character passwords, no composition rules, common/repetitive/name-based passwords refused; login throttled per address+account and per account (30 failures / 15 min regardless of client address); SSO via OIDC (PKCE, nonce, signed ID tokens) or SAML (signed assertions, replay protection); SSO can be required for everyone but owners. |
| V3 Sessions | HttpOnly `SameSite` cookies (`Secure` on HTTPS), 15-minute access tokens, rotating 30-day refresh sessions; password change, admin reset, deactivation and "sign out everywhere" revoke sessions server-side. |
| V4 Access control | Org, workspace and project roles intersected with token scopes on every call; resources you cannot see return 404; MCP tools enforce the same rules. |
| V5 Validation | Pydantic schemas on every input; SAML parsing without entities or network; inbound GitHub/GitLab payloads signature-checked and size-capped; request bodies over 10 MB refused. |
| V7 Errors and logging | RFC 9457 problems without stack traces; structured JSON logs; an audit log of every domain change, sign-in (success and failure), SSO, provisioning, export and MCP tool call, with configurable retention. |
| V8 Data protection | `Cache-Control: no-store` on API responses; third-party secrets encrypted at rest (Fernet, key derived from `GLASSHAUS_SECRET_KEY`); data export excludes credentials. |
| V9 Communications | Run behind HTTPS (HSTS is sent when `GLASSHAUS_PUBLIC_URL` is HTTPS); outbound webhooks verify TLS and pin the checked address. |
| V10 Malicious code | Dependency and image scanning in CI (pip-audit, npm audit, Trivy, gitleaks). |
| V12 Files and resources | Outbound requests refuse loopback, link-local and metadata addresses (SSRF); no redirects followed. |
| V13 API | CSRF tokens for cookie sessions; CORS off unless configured; per-principal rate limits on REST/SCIM (`GLASSHAUS_API_RATE_LIMIT_PER_MINUTE`) and MCP; strict CSP and `nosniff`/`DENY` headers on the web app and API. |
| AI (optional) | Off unless a server provider and an admin switch are both set; read-only with no tools, so model output can only be shown or proposed; project text sent as delimited untrusted data; least data per feature (search sends no task content); runs with the caller's permissions; per-person rate limit; every request audited without content. See `docs/ai.md`. |
| V14 Configuration | All configuration from environment; secrets generated by `setup.sh`, never committed; non-root, read-only containers with dropped capabilities. |

## Operator checklist

- Serve the web app and MCP server over HTTPS; set `GLASSHAUS_PUBLIC_URL` / `GLASSHAUS_MCP_PUBLIC_URL`.
- The API port (8471) is for API clients; bind it to `127.0.0.1` (`GLASSHAUS_BIND_ADDRESS`) or firewall it
  if only the web app and MCP server need it. When it is reachable directly, client addresses in logs can be
  spoofed through `X-Forwarded-For`; account-level throttling does not depend on them.
- Keep `GLASSHAUS_SECRET_KEY` secret and stable (it signs sessions and encrypts stored integration secrets).
- Review **Admin → Audit log** and set retention under **Admin → Data & retention**.
- Copy backups off the host.
- If you turn on the AI assistant, choose a provider whose data terms suit you (or a local model with
  `GLASSHAUS_AI_PROVIDER=openai`) and keep `GLASSHAUS_AI_API_KEY` in `.env` only.
